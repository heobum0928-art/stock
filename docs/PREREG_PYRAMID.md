## 0. 배경 — 2026-08-16에 이미 설계된 것을 백테스트로 검증한다

`docs/would_change_log.md` 2026-08-16 항목에 사용자 제안("이미 이기고 있는 포지션에
증거금을 추가로 실어서 사이즈를 키우자")과 AI 2개(Manus, Gemini) 자문을 거친 안전기준이
이미 있다. 그때 조건은 **"51건 이후 검토"**였다 — 51건 관문은 2026-08-28에 통과했으므로
전제조건은 충족됐다.

**다만 이건 새 전략이 아니라 기존 실거래 포지션의 관리 방식을 바꾸는 것**이라, 조용한급등·
PROM롱처럼 모의로 며칠 돌려보는 방식이 안 맞는다. 실거래 봇의 포지션 관리 로직 자체를
바꾸는 문제라, **1년치 실측 데이터(research/m5bt/, 805종목, 신호 2,399건)로 먼저
백테스트한다.** 이 데이터셋은 이미 이 프로젝트의 거의 모든 검정(DD_SPEED, V1_notrail,
미러롱 등)에 재사용돼 왔다.

### 8/16에 이미 지적된 위험 — 잊지 않는다
숏은 롱과 달리 반대방향 손실에 상한이 없다(가격 상승엔 이론상 한도 없음). "반전 확신하고
불타기했는데 실제론 계속 갔다"는 패턴이 이미 한 번 실제 사고(HFT -221%)로 났었다.
**그래서 판정 기준에 평균·신뢰구간뿐 아니라 꼬리위험(최악의 경우) 검사를 필수로 넣는다**
(CLAUDE.md 4항 — 지표 하나로 결론 내지 않는다, 이 문제는 특히 꼬리가 중요하다).

## 1. 규칙 (지금 고정, 변경 금지) — 2026-08-16 Manus안 그대로

| | 값 |
|---|---|
| 트리거 | 명목가 기준 **+25% 유리** (트레일링 무장점 +15%보다 확실히 높게 — "이미 반전 충분히 확인된 뒤"만) |
| 조건 | **손실 중엔 추가 금지.** 트리거 자체가 유리한 방향이라 사실상 자동 충족되지만 명시적으로 재확인 |
| 추가량 | 원 증거금의 **50%** (2배 몰빵 금지, Manus 8개 통제 중 2번) |
| 추가 횟수 | **1회만** (연속 불타기 금지) |
| 추가 후 | 평균단가를 **가중평균으로 재계산**: `(P0×qty0 + P_add×qty_add) / (qty0+qty_add)` |
| 손절 | 새 평균단가 기준 **동일 -40%** 그대로 적용(손절 규칙 자체는 안 바꾼다 — V5_stop30 교훈) |
| 트레일링 | 새 평균단가 기준으로 무장점(+15%)·반납폭(10%) 재계산해서 계속 적용 |
| 보유 | 48시간 고정 (변경 없음) |
| 비교 대상(신호셋) | `research/m5bt/events.pkl`의 2,399건 — margin_short 원본봇 신호(7h+30~40%) |

**Gemini의 더 보수적인 대안**(새 증거금 대신 "이미 확보된 이익 범위 안에서만, 손절선을
이익구간으로 올리고 극소량만 추가")은 **2차 검정으로 남겨둔다** — 이번 1차가 기각되면
자동으로 폐기, 통과해도 곧바로 채택하지 않고 별도로 다시 백테스트한다(CLAUDE.md 5항 —
여러 안을 동시에 던져놓고 통과하는 것 고르지 않는다. Manus안 하나만 먼저 확정 검정).

## 2. 백테스트 방법론

`research/m5bt/engine.py`의 이벤트 사전계산 구조(`scan`/`evaluate`)는 **고정 사이즈
단일 포지션**을 전제로 설계돼 있어 그대로는 불타기를 표현할 수 없다(재확인 완료 —
`SigEvents`는 진입가 P0 하나와 그로부터의 이벤트만 담는다). 그대로 억지로 끼워 맞추면
버그가 나기 쉬우므로, **새 스크립트(`research/m5bt/pyramid_bt.py`)를 별도로 작성**한다:

1. `events.pkl`에서 심볼·진입시각(t0)·진입가(P0)를 그대로 재사용(2,399건 신호셋 동일).
2. 해당 구간의 원시 5분봉(`pq/{sym}.npz`)을 다시 읽어 **봉 단위로 직접 시뮬레이션**한다
   (기존 엔진처럼 O(1) 이벤트 사전계산이 아니라 단순 for문 — 2,399건×576봉=138만
   스텝이라 성능 문제 없음, 정확성을 우선한다).
3. 각 신호마다 **두 결과를 동시에 계산**(짝비교, CLAUDE.md 3항):
   - **기준(V0)**: 현행 그대로(불타기 없음, 이미 `v1_bt.py`로 재현 검증된 로직 재사용)
   - **처리(불타기)**: +25% 유리 도달 시 1회 50% 증액, 그 지점부터 새 평균단가로 나머지
     시뮬레이션 계속
4. 수수료·펀딩비는 기존 엔진과 동일 가정(편도 0.06%, 실측 펀딩) 그대로 적용.
   추가 진입분도 별도 진입수수료 부과(왕복 아님, 편도).

## 3. 판정 기준 (결과 보기 전 확정)

주지표: 짝차이 평균(증거금 기준 %, 신호당 원래 배정 자본 기준으로 정규화)

### 채택 후보 — **전부** 충족
1. 짝차이 평균 **> 0**
2. 일-블록 부트스트랩(신호별 그룹) **95% CI 하한 > 0**
3. 최대기여 단일 거래 제외 시 **부호 유지**
4. 홀드아웃(짝수/홀수 월 분리 또는 `events.pkl`의 기존 hold 플래그) 부호 일치
5. **꼬리위험 검사(필수, 이 검정 고유)**: 불타기 쪽의 **최악 10건 평균**이 기준(V0) 쪽
   최악 10건 평균보다 **더 나쁘지 않아야 한다**. 평균이 개선돼도 이 조건이 깨지면
   "평균은 좋아졌지만 꼬리가 더 위험해졌다"로 별도 기록하고 **미채택**.
6. 참고 기록(판정 아님): 불타기 발동 비율(전체 신호 중 +25% 도달 비율), 발동 시
   승률 vs 미발동 시 기준 승률

### 즉시 기각
- 1~5 중 하나라도 미충족

## 4. 이 문서가 막는 것
- 평균만 보고 꼬리위험 검사(5번)를 생략하는 것 — 이게 이 검정을 하는 핵심 이유다
- Gemini의 보수적 대안과 결과를 비교해서 더 좋은 쪽을 고르는 것(사후 선택, CLAUDE.md 5항)
- 통과해도 바로 실거래 코드에 반영하는 것 — 백테스트 통과는 "실거래 구현을 설계할 근거가
  생겼다"까지다. 실거래 코드 반영은 별도 구현·검증 후 사용자가 직접 결정한다(CLAUDE.md 6항)
- 추가 트리거(+25%)나 추가량(50%)을 결과 보고 조정하는 것

## 5. 사전 선언
**나는 통과를 5:5 정도로 본다.** 평균 개선 자체(+15%p 유리한 지점에 더 실었으니 이긴
거래의 크기가 커짐)는 상당히 그럴듯하지만, 8/16에 지적된 꼬리위험(반전 후 재반전)이
실제로 얼마나 되는지는 데이터를 보기 전엔 모른다. 이 예측은 판정 기준이 아니라 기록용이다.
